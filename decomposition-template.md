# CampusFlow — практическая работа №1

## 1. Общее понимание проекта

**Суть проекта:** CampusFlow — учебное веб-приложение, в котором студент ищет подходящее учебное мероприятие, применяет фильтры к каталогу, изучает подробности выбранного события, может отметить его как избранное и подать заявку на участие.

**Ключевой пользовательский путь:** поиск → фильтрация → открытие карточки мероприятия → (опционально) добавление в избранное → подача заявки → получение подтверждения → переход в раздел «Мои события».

## 2. Экраны и адресация

| № | URL / экран | Назначение | Ключевые блоки | Целевое действие |
|---|---|---|---|---|
| 1 | `/events` | Список всех мероприятий | Шапка, строка поиска, сортировка, фильтры по темам, боковые фильтры, карточки, постраничная навигация | Найти нужное мероприятие и перейти к нему |
| 2 | `/events/:id` | Подробная страница мероприятия | Шапка, ссылка назад к каталогу, сведения о событии, кнопка записи, избранное, вкладки, текстовое описание | Подать заявку или сохранить в избранное |
| 3 | `/events/:id/register` | Форма подачи заявки | Шапка, форма ввода, обязательные поля, чекбокс согласия, отображение ошибок, состояние загрузки, экран успеха | Успешно отправить заявку |

Пункты `/my-events` и `/profile` присутствуют в навигационном меню макета, однако задание не содержит для них отдельных экранов. В текущей практической работе их стоит рассматривать как ссылки на внешние разделы, а не проектировать как самостоятельные страницы без явного требования.

## 4. Разбиение на компоненты

| Компонент | Используется на | Принимаемые данные | Состояния | Причина выделения |
|---|---|---|---|---|
| `SiteHeader` | Все три страницы | `currentRoute`, список пунктов меню | активный пункт, мобильный вид | Появляется на каждой странице без изменений |
| `EventCard` | Каталог | `title`, `category`, `date`, `format`, `seats`, `isFavorite`, `id` | избранное вкл/выкл, есть места/мест нет | Является повторяющимся элементом |
| `FavoriteButton` | Карточка и страница события | `isFavorite`, `label` | выключено/включено, в фокусе | Логика взаимодействия одинакова в обоих местах |
| `SearchBar` | Каталог | `value`, `placeholder` | пусто/заполнено/идёт загрузка | Обладает собственной логикой обработки запроса |
| `FilterPanel` | Каталог | текущие фильтры, доступные варианты | неактивно/выбрано/сброшено, открыта/закрыта на мобильных | Имеет своё внутреннее состояние и адаптивное поведение |
| `Pagination` | Каталог | `currentPage`, `totalPages` | текущая страница/недоступна | Универсальный переиспользуемый элемент управления |
| `EventTabs` | Страница мероприятия | `activeTab`, список вкладок | активна, наведение, фокус | Отвечает за переключение отображаемого контента |
| `RegistrationForm` | Форма регистрации | значения полей, ошибки, статус отправки | пусто/заполнено/ошибка/загрузка/успех | Содержит развитую самостоятельную логику |
| `FormField` | Форма регистрации | `id`, `label`, `value`, `error`, `required` | пусто/заполнено/ошибка/недоступно | Единая логика отображения поля и его ошибки |
| `Button` | Каталог, страница события, форма | `type`, `disabled`, `loading` | обычное/наведение/фокус/недоступно/загрузка | Общие правила поведения кликабельных элементов |

### Что сознательно не выносится в отдельные компоненты

- Заголовок и вводный текст конкретной страницы остаются частью самой страницы, так как пока не повторяются в других местах.
- Блок с метаданными события остаётся внутри `EventCard` или страницы мероприятия — отдельной бизнес-логики под него пока нет.
- Footer можно вынести отдельно в дальнейшем, но для текущей практической работы достаточно оставить его статичным структурным блоком без собственного поведения.

## 6. Логика основных сценариев

1. **Поиск:** пользователь вводит текст → список результатов каталога обновляется → если совпадений нет, отображается сообщение «ничего не найдено».
2. **Фильтрация:** пользователь выбирает нужные фильтры и применяет их → набор карточек пересчитывается; активные фильтры должны выделяться визуально и допускать сброс.
3. **Избранное:** на карточке или на странице мероприятия клик переключает состояние `выключено ↔ включено`, при этом смысл самого элемента не меняется.
4. **Запись на мероприятие:** клик по кнопке «Записаться» запускает загрузку → далее либо успешный результат, либо ошибка; если мест нет, кнопка становится неактивной заранее.
5. **Отправка формы регистрации:** при сабмите повторное нажатие блокируется → отображается загрузка → в случае успеха показывается сообщение и происходит переход в «Мои события», в случае ошибки — сообщение рядом с проблемным полем.

## 7. Семантическая разметка

Предполагаемая структура для страницы каталога:

```text
<body>
  <header>
    <a>логотип</a>
    <nav>основное меню</nav>
  </header>
  <main>
    <section>
      <header>заголовок и описание раздела каталога</header>
      <form role="search">поле поиска и сортировка</form>
      <div>
        <aside>панель фильтров</aside>
        <section>блок результатов
          <article>карточка отдельного мероприятия</article>
          <nav>постраничная навигация</nav>
        </section>
      </div>
    </section>
  </main>
  <footer>служебные сведения</footer>
</body>
```

Пояснения к выбору тегов:
- `header` — верхняя часть страницы, общая для всего сайта;
- `nav` — блок навигационных ссылок;
- `main` — уникальный содержательный блок страницы;
- `section` — смысловые разделы страницы;
- `aside` — дополнительная панель, сопутствующая основным результатам;
- `article` — карточка мероприятия как самостоятельная единица контента;
- `form` — элемент для ввода и фильтрации данных пользователем;
- второй `nav` — пагинация тоже относится к навигации;
- `button` — интерактивное действие в интерфейсе;
- `a` — переход по другому адресу.

Каждое поле формы регистрации должно сопровождаться связанным `label`, а текст ошибки — быть привязан к полю программно (например, через `aria-describedby`). Визуальное состояние фокуса нельзя убирать без доступной альтернативы.

## 8. Поведение при разных размерах экрана

| Блок | Desktop | ~1024 px | ~768 px | ~375 px |
|---|---|---|---|---|
| Шапка | логотип и горизонтальное меню | отступы уменьшаются | меню может переноситься на вторую строку | компактный вариант шапки |
| Сетка карточек | 3 колонки | 2 колонки | 1–2 колонки в зависимости от ширины | 1 колонка |
| Панель фильтров | размещена сбоку | остаётся сбоку | превращается в раскрывающуюся панель или диалог | раскрывающаяся панель/диалог на всю ширину |
| Поиск и панель инструментов | в одну строку | строка может сохраняться | элементы располагаются друг под другом | элементы располагаются друг под другом |
| Форма | ограниченная ширина блока | сохраняет комфортную ширину | один столбец | один столбец, без выхода за пределы viewport |
| Пагинация | горизонтальное расположение | структура сохраняется | интервалы между элементами уменьшаются | не должна провоцировать горизонтальную прокрутку |

Ключевое требование: ни блок карточек, ни форма не должны вызывать горизонтальный скролл при ширине 375 px.

## 9. Открытые вопросы и допущения

1. **Разделы «Мои события» и «Профиль» есть в меню, но макетов и требований к ним нет.** Принятое допущение: в рамках практической работы №1 они рассматриваются только как внешние точки перехода, без реализации отдельных экранов.
2. **Не описано, как ведёт себя сортировка при изменении фильтров.** Принятое допущение: выбранный способ сортировки сохраняется, а результаты пересчитываются уже с учётом новых фильтров.
3. **Не указано, откуда берутся данные и как сохраняется избранное.** Принятое допущение: на данном этапе используются mock-данные и хранение состояния в оперативной памяти приложения; проектирование API откладывается до появления соответствующего требования.
4. **Не описано поведение при ошибке во время отправки заявки.** Принятое допущение: пользователю показывается понятная формулировка ошибки и предоставляется возможность повторить попытку отправки.
5. **Не определено, как боковые фильтры должны выглядеть на мобильных устройствах.** Принятое решение: использовать выдвижную панель (drawer) или модальное окно с отдельной кнопкой открытия и явным применением выбранных фильтров; этот выбор нужно закрепить до начала вёрстки.

## 10. Возможные риски

- Слишком длинные названия мероприятий могут нарушать высоту карточек → предусмотреть перенос текста и не задавать жёсткую фиксированную высоту заголовка без необходимости.
- Длинные значения в фильтрах могут не помещаться в элементы управления → протестировать на реальных, а не тестовых данных.
- При вёрстке только по desktop-макету легко упустить состояния загрузки/недоступности → закладывать их в компоненты ещё до стадии стилизации.
- Боковая панель на мобильных может занимать слишком много места на экране → применять раскрывающийся контейнер или диалоговое окно.
- Ошибка формы, не связанная программно с полем, снижает доступность интерфейса → заранее продумать `id` полей и связь ошибок через `aria-describedby`.
